# Languages

An application built on Rapyd Admin speaks the languages listed in `config('rapyd.locales')`:

```dotenv
RAPYD_LOCALES=en,it,fr
```

The default language is `config('rapyd.locale')` (`APP_LOCALE`, or `RAPYD_LOCALE` when they differ) and has no URL
prefix; every other language is the first segment of the URL: `/companies` and `/it/companies` are the same page. One language enabled (the default): no switcher, no
redirects, nothing changes.

## How the language is chosen

`Zofe\Rapyd\Localization\SetLocale`, in the `web` middleware group, in this order:

1. the URL prefix (`/it/...`): the language of the page, remembered in the session;
2. for a URL without prefix: the language remembered in the session, then the preference of the logged-in user
   (`users.locale`), then the browser's `Accept-Language`. When one of them is not the default language, a `GET`
   page is redirected to that language; other requests (the Livewire update endpoint, forms) just run in it;
3. the switcher adds `?clang=1` to say the choice is deliberate: it is remembered in the session and, for a
   logged-in user, saved in `users.locale`.

Module routes are registered with the prefix of the current request (`Locales::routePrefix()`), so route names are
the same in every language and the breadcrumbs, the menus and the components need nothing. Two consequences:
`route:cache` is not usable with more than one language enabled, and links are built with `route_lang()` (or the
`x-rpd::` navigation components, which use it) so they keep the language of the page. `url_lang($locale, $change)`
gives the current page in another language: it is what the switcher (`layout::includes.locale_switcher`, in both
navbars) links to.

### The application's own routes

Module routes get the prefix by themselves. The routes of the application (`routes/web.php`: the home page, a
landing…) are Laravel's, so wrap them the same way, or `/it/` is a 404 while `/it/companies` works:

```php
use Zofe\Rapyd\Localization\Locales;

Route::prefix(app(Locales::class)->routePrefix())->group(function () {
    Route::get('/', Home::class)->middleware(['web'])->name('home')
        ->crumbs(fn ($crumbs) => $crumbs->push(__('Home'), route_lang('home')));
});
```

## Translating the texts

Texts are English phrases, written as they are in the views; a `Lang/{locale}.json` file next to them maps each
phrase to its translation:

```json
{
    "Business Name": "Ragione sociale",
    "No users yet.": "Ancora nessun utente."
}
```

Three things make a phrase translatable:

- `{{ __('Back') }}` around raw text in the HTML (buttons, table headings, `<dt>`);
- the `label`, `title`, `placeholder`, `actionLabel` attributes of the `x-rpd::` components, which translate them
  themselves: `label="Business Name"` is enough;
- the same in the code generated by `rpd:make`: column headings, labels and buttons come out as phrases.

Where the files live and who loads them:

| Texts of | File | Loaded by |
|---|---|---|
| the package (components, layouts, bundled modules) | `resources/lang/{locale}.json` of rapyd-admin | `RapydServiceProvider` |
| a module of the application | `app/Modules/Blog/Lang/{locale}.json` | `ModuleServiceProvider` |
| a module package (shop, demo…) | `Lang/{locale}.json` of the package | `RapydModuleServiceProvider::bootAppModule()` |
| the rest of the application | `lang/{locale}.json` | Laravel |

The catalogues add up: a phrase translated by the package needs no line in the module's file. PHP language files
(`Lang/en/user.php`, `__('auth::user.name')`) keep working for structured messages, with parameters or plurals; the
JSON phrases are for the interface. One rule: a phrase must not be the name of a PHP language file (`Auth`,
`Validation`, `User` when `Lang/en/user.php` exists), because `__()` would return that file instead of a translation.
`rpd:lang` reports them.

The package ships `en` (the phrases), `it` (reviewed) and `es`, `fr`, `de`, `pt_BR` translated by a machine and
waiting for a review: `.rpd-lang.json` next to the catalogues lists them. Contributions are welcome.

## `rpd:lang`: collecting and translating the phrases

```bash
php artisan rpd:lang                 # every module of app/Modules into its Lang/, the rest into lang/, every enabled locale
php artisan rpd:lang it fr           # only these locales
php artisan rpd:lang --module=Blog   # one module
php artisan rpd:lang --path=vendor/zofe/shop-module --out=vendor/zofe/shop-module/Lang   # a package
php artisan rpd:lang --literals      # list the raw HTML texts no __() reaches
php artisan rpd:lang --translate     # fill the pending phrases with the AI of ai-module, marked for review
php artisan rpd:lang --check         # exit 1 while phrases are pending: for CI
php artisan rpd:lang --prune         # drop the phrases no view uses any more
```

It scans the Blade views and the Livewire components (`__()`, `@lang()`, `trans()`, the static attributes of the
`x-rpd::` components), adds the new phrases to the `.json` files untranslated (value = phrase, so nothing breaks)
and keeps them as *pending* in `.rpd-lang.json`. Translate them by hand in the `.json`, or with `--translate` when
[ai-module](https://github.com/zofe/ai-module) is installed with a provider configured: those come back marked
*machine-translated*, to review. Translations already there are never overwritten.

## The user's language

`users.locale` (added by the Auth module migration) holds the language a user chose with the switcher; the
middleware brings a logged-in user back to it. An application may set it elsewhere (a profile form) with the same
effect.

## What is not covered

The content of the database (product names, articles) is not translated by the catalogues: that is a model
concern (translated columns, a JSON column with a trait) and a choice of each application.
